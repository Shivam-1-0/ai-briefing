## Worth Reading Closely

### OpenAI's four-part prompt framework

What happened: OpenAI's latest model guide argues that most disappointing AI outputs trace back to one cause — the prompt left a decision unmade, and the model filled it in with a guess the person never sees coming. The guide names four decisions every ask makes, whether you state them or not: the result wanted, who it's for, the context and limits that apply, and what counts as "done." OpenAI's own example is "write a toast for my sister's wedding" — a complete-sounding request that still leaves length, tone, audience, and finish condition entirely up to the model.

Why it matters at the mechanism level: an LLM doesn't return an error when a prompt under-specifies a decision — it silently samples a plausible default and proceeds, and that default can differ between runs of the identical prompt. This is the actual mechanism behind "AI is inconsistent": not model unreliability, but unresolved decision points being resolved differently each time. OpenAI's counterintuitive second point — that adding more words usually makes this worse, not better — follows from the same mechanism: padding a prompt with restatements and caveats doesn't add missing decisions, it adds noise the model has to weigh against the signal, diluting the four real decisions rather than reinforcing them.

For an n8n-based agent stack, this is directly actionable rather than abstract advice. A prompt node that leaves any of the four slots as free text invites run-to-run variance that looks like flakiness in testing but is actually the model resolving an unspecified decision differently each time. The fix is structural: template every prompt-generating node with explicit fields for result, audience, context/constraints, and a done-condition, so none of the four is ever left to the model's discretion. (Confirmed — OpenAI, via TAAFT)

### Hacker News "Goalposts": a decade of AI predictions, scored

What happened: someone collected every AI challenge posted in Hacker News comments going back ten years — passing a Turing test, driving in snow, cleaning a toilet — onto a single page, then opened it for public voting. The split that emerged: screen-bound tasks (writing code, passing text-based tests) are now widely seen as solved, while physical-world tasks (driving everywhere, cleaning) are widely seen as unsolved, even when the physical task sounds simpler to a person.

Why it matters at the mechanism level: an LLM learns a task by reading enormous amounts of labeled examples of inputs mapped to correct outputs. Code and text are already stored natively in that format — millions of worked examples exist as plain, structured training data. A task like "clean a toilet" has no equivalent corpus: a video shows the result, not the forces applied, the grip pressure, or how the motion should adapt when the bathroom layout changes. There's no abundant, symbolic record of the decision-making involved, so there's nothing comparable for a model to learn from at scale. That gap — not task "difficulty" as a human would judge it — is what actually predicts which jobs AI automates first.

This is a useful filter for deciding what to hand to an agent versus what to leave alone: if a task's inputs and correct outputs can be represented as abundant, labeled, symbolic data (text, code, structured records), it's a strong current candidate for automation. If the task depends on embodied, physical feedback that isn't captured in any existing dataset, treat "it looks simple" as no signal at all about whether an agent can do it. The caveat worth keeping in mind: these are Hacker News readers who opted into voting, not a scientific sample, so treat the percentages as a temperature check rather than a measurement. (Reported — informal vote, via TAAFT)

## One Thing to Learn

Anthropic's free course, **"AI Capabilities and Limitations"** (13 lessons, academy.claude.com, part of Claude Academy). It's built for people with no technical background, and it directly answers a question that's easy to get wrong by trial and error: when should you trust a model's output versus double-check it? The course walks through concrete failure patterns — weak coverage on topics that are rare or recent relative to training data, and context loss as a conversation gets long — rather than vague warnings about "hallucination."

The 20-minute payoff: once you can name which failure mode an odd output matches, you stop treating every mistake as a mystery and start designing around it. For someone wiring Claude into n8n workflows, that means knowing in advance where a workflow needs a retrieval step (to cover the rare/recent gap) or a context-reset step (to cover long-chat drift), instead of discovering both gaps after a workflow has already shipped something wrong.
