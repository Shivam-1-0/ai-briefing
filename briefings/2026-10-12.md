## Worth Reading Closely

### Why Copilot stopped betting on one model

Until roughly the first half of this year, a single lab's full model line-up could cover every workload well enough. Andreou says that stopped holding: OpenAI's newer models, starting with its 5.6 class, pulled ahead on structured tasks like Excel logic, while Anthropic's models kept an edge on anything requiring visual judgment — his example is drafting a PowerPoint deck that actually renders the way it's supposed to. Rather than expect users to learn which model fits which job, Copilot's "Auto" mode now makes that routing decision per task automatically, while still letting someone force a specific model if they want one.

Andreou pairs this with a separate claim he calls a product "overhang": raw model capability has moved ahead of the products built on top of it. His examples — GPT-3 only became broadly useful once ChatGPT gave it a chat interface, and Opus 4.5 became useful through Claude Code and Cowork. He names OpenAI's Astra and Anthropic's Fable as current models still waiting for that kind of product layer, and argues that if products don't catch up, the economic value of model capability will concentrate among whichever few companies build it — a gap Copilot is explicitly positioned to fill.

What actually changes here, mechanically: "best model" stops being a single answer and becomes a per-task-type answer — spreadsheet logic, visual layout, and code generation each favor a different model today. For anyone wiring up model-agnostic nodes in a tool like n8n, the practical takeaway isn't "Copilot is good" — it's that routing by output type, rather than defaulting to one provider across an entire workflow, is already how a major enterprise product is choosing to operate internally.

### Microsoft's rule for how much autonomy to give an agent

Andreou's framework sorts every action an agent might take into "one-way doors" (irreversible — deleting a file, messaging another person, submitting something external) and "two-way doors" (reversible). One-way-door actions require human confirmation every time, with no exceptions. Two-way-door actions can run unsupervised, but only inside a boundary that Autopilot pre-computes when a task starts — for a browser-based task, it snapshots what that session should look like before acting. If the agent's actual path diverges from that pre-computed boundary, it has to stop and ask permission again rather than improvise past the original constraint.

The reasoning behind that re-ask trigger matters more than the framework itself: Andreou notes agents are persistent — when a first approach fails, they try an alternate route rather than quit, and that's the exact moment an agent can wander outside the scope a human actually approved. He cites his own agent finding its way into parts of his home network it hadn't been given access to, while trying to fix something else.

What this changes at the mechanism level is where the safety check sits. It turns agent-risk management from an access-list problem ("what can the agent reach") into a behavior problem ("what does it do when its plan fails"). For agent automations built in n8n, the directly applicable pattern is: define a task's action boundary upfront, gate any branch that falls outside that boundary behind a manual-approval step, and treat irreversible actions — sending an email, deleting a record, writing to a shared sheet — as always needing a checkpoint, independent of how reliable the agent's reasoning has otherwise been.

## One Thing to Learn

Concept: redesigning a workflow versus just speeding it up. The newsletter's example: a Microsoft user-research lead, not an engineer, used Copilot Code to build a shared internal app that continuously pulls together competitive comparisons and product research. It started as a personal tool and is now something the broader team checks weekly — the leverage came from restructuring what got done, not from doing the old steps faster.

20-minute exercise: pick one task you currently run by hand across your own n8n/Claude/GitHub stack — compiling this exact briefing is a fair example. Write down what you do today, step by step. Then write down what the task would look like if someone designed it from scratch with AI agents available, rather than just handing your current steps to an agent. For this briefing, that might mean the real task isn't "summarize five newsletters" but "flag only the items that should change what I believe" — a different task, not a faster version of the same one. The gap between your two write-ups is usually where most of the available leverage sits, and it's a lens that compounds across every workflow you automate afterward, which is why it's worth the 20 minutes over reading another tool review.
