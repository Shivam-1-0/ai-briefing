## Worth Reading Closely

### A restricted-access model just gave Firefox a free, machine-speed security audit

OpenAI released GPT-6 Cyber, a model tuned specifically for vulnerability discovery and exploit reasoning rather than general chat. Internally it's rated "Critical" under OpenAI's own risk framework, which is why it isn't a general release — distribution is limited to vetted security teams rather than shipped as a product. Mozilla used it against Firefox, a codebase a senior Mozilla engineer described as "one of the world's most hardened and scrutinized," already combed over by earlier-generation AI models. GPT-6 Cyber still found 81 previously unknown high-severity holes and showed that 30 bugs Mozilla already knew about were worse than their existing severity rating suggested. Each finding arrived with a suggested fix attached, and Mozilla has already shipped patches for many.

What actually changes here is the economics of finding bugs, not just the existence of a smarter model. Locating a real vulnerability in mature, well-audited code used to require scarce specialist time measured in weeks; a model run at machine speed compresses that into an automated pass that also hands back a candidate patch. That cuts both ways: a defender gets a free, repeatable audit of code they thought was already clean, but the same capability class, run by someone without Mozilla's intentions, would hunt exploits at the same speed. That asymmetry is the actual reason OpenAI gated access instead of shipping GPT-6 Cyber broadly — the risk isn't the model existing, it's who gets to run it. For anyone building agents, it's also a concrete example of what a narrow, domain-specialized agent looks like in practice: not a chatbot that answers questions about security, but one that works a codebase systematically and returns verified, actionable output. *(Confidence: Confirmed. Source: OpenAI, reported via TAAFT and Vaibhav Sisinty.)*

### Claude's new finance feature is really a template for building a read-only, standing agent

Anthropic's Personal Finance beta connects Claude to a user's bank through Plaid, a third-party data aggregator, rather than taking bank credentials directly. Plaid handles authentication and hands Claude a scoped, read-only, revocable access token to transaction data — Claude never sees a password, and per Anthropic, financial-hub conversations are excluded from model training. Once connected, Claude reads up to two years of transaction history and flags things a person would otherwise have to notice manually: charges that hit twice, fees that crept up, subscriptions that quietly got more expensive.

The mechanism worth noticing is the shape of the automation, not the finance use case specifically: this is a standing, read-only observer running a recurring check against a live data feed, rather than a single prompt-and-answer exchange. That's the same pattern anyone building on n8n is already reaching for when they wire a scheduled trigger to an API pull and an LLM-based anomaly check — Anthropic has simply productized it end to end for one dataset. For whom it matters: directly, for anyone trying to replicate "watch my transactions and flag anomalies" as an automation rather than a manual monthly review; and more broadly, for anyone evaluating what kind of access to grant an agent at all — the Plaid layer is doing the real safety work here, not Claude's own judgment. Separately, Vaibhav Sisinty's newsletter notes India already has a comparable rail in the Account Aggregator framework, which could plausibly carry an equivalent feature domestically, though no such rollout has been announced. *(Confidence: Confirmed on the feature itself; Speculative on any India-specific rollout. Source: Anthropic, via Vaibhav Sisinty.)*

## Agents & Automation Watch

Two items this cycle matter specifically for an n8n/Claude/GitHub agent stack, beyond the security story above.

Meta's acquisition of Conductor, a coding-agent app, comes bundled with a hard shutdown of its cloud service on November 20. Anyone with a workflow depending on Conductor's hosted execution needs to export data and move off before that date. The pattern is worth noting on its own: acquisitions of agent tooling are increasingly ending in short wind-down windows rather than gradual sunsets — a standing risk to weigh before building a dependency on any single third-party agent platform.

Sarvam's Prism, released out of Bengaluru, is a small model built for exactly one job: picking from a fixed menu of options in about 44 milliseconds, instead of generating open-ended text. That's the shape of model an orchestrator actually wants at a routing or classification step — intent detection, tool selection, branch logic — where a full chat-completion round-trip adds latency the step doesn't need. Worth testing as a lightweight routing node ahead of a heavier model call, rather than defaulting every decision point in an n8n flow to a general-purpose chatbot.

Nothing new today on orchestration frameworks, MCP, or agent-to-agent protocols specifically — this cycle's automation-relevant news was point capabilities (a security-scanning model, a fast routing model) rather than anything framework-level.

## One Thing to Learn

**The Plaid/Account-Aggregator pattern: read-only, revocable access through a middleman, instead of handing over credentials.**

Anthropic's Personal Finance feature doesn't give Claude a bank password — it gives Claude a scoped token issued by Plaid, an aggregator that already holds a vetted connection to the bank. Claude can read transaction data; it cannot authenticate as the user; and access can be revoked from either the bank's side or Plaid's side without ever touching the user's actual credentials. It's the same shape as the OAuth2 flow you already use every time you connect a Google Sheet or Gmail account into an n8n workflow, just applied to a bank feed instead.

The 20-minute version worth doing: open Plaid's public docs and read through how a "Link" token exchange actually works end to end — issue a link token, have the user authenticate with their bank through Plaid's UI, exchange a public token for a permanent access token scoped to specific data. Then compare that directly to how n8n's own OAuth2 credential nodes negotiate scoped access. The plumbing differs, but the shape is identical, and understanding it is what lets you reason precisely about what any agent you build can actually do with a connected account — and what it structurally can't.
