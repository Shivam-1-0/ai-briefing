## Worth Reading Closely

### Gemini 4 Neon shows Google now treats "mid-tier" as a pricing decision, not a capability ceiling

Google's periodic-table naming scheme (Argon, Carbon, Hydrogen, now Neon) was supposed to map to a capability tier — Carbon the flagship, lighter elements for cheaper, faster variants. Neon breaks that assumption: despite carrying the "lighter" label, it edges Google's own top-end Carbon on the Artificial Analysis Intelligence Index (61) and, on Google's internal testing, beats Claude Opus 5.5 and GPT-6.2 Sol on 16 of 19 benchmarks, with its widest margins in long-document work, office automation, and cyber tasks. It's priced at $3/$15 per million input/output tokens — a quarter below both Opus 5.5 and full-price Carbon — with a 1M-token context window and cached input at $0.15 per million tokens.

The mechanism that matters for anyone choosing models for an automated pipeline: Neon decouples "frontier-level benchmark score" from "frontier-level price," which previously moved together. A workflow that routed easy tasks to a cheap model and hard tasks to an expensive one now has a third option — a model that scores near the top of the leaderboard at a quarter of the flagship price, which changes the cost-benefit math for any router that assumed quality and price were the same knob. The more speculative part is why Google can now ship a fourth frontier-adjacent model in under two months when it spent most of 2026 being the slowest of the major labs to ship. Minkai Xu's pre-launch post about recursive self-improvement (RSI) — AI systems helping design their successors — is a single internal comment, not a confirmed mechanism, so treat it as a plausible explanation rather than an established fact. What's confirmed is the output: a faster shipping cadence that's now showing up in API pricing and benchmark tables, not just announcements. *(Confidence: Confirmed on pricing/benchmarks, from Google's own blog and Artificial Analysis; Speculative on the RSI explanation for Google's pace. Sources: TLDR AI, The Rundown AI.)*

### AI redesigning the chips that run AI is no longer a research demo — it shipped into real silicon

OpenAI let its models rework the floating-point math units on the first chip OpenAI itself designed (its Jalapeño AI accelerator). The result: one component came out roughly 15% smaller and completed its job in about half the time, and those specific changes held up when the chip was actually fabricated — not just simulated. OpenAI then pointed the same approach at AMD's flagship GPU design, after AMD's own engineers had already run their usual hand-optimization pass. The AI found up to 14% further improvement on top of that human-optimized baseline. OpenAI frames the AMD result as roughly a year's worth of typical hardware-design progress compressed into under five months; AMD has committed some of those changes to a chip already in its manufacturing pipeline, with more queued for future generations.

The mechanism, stripped of framing: chip layout design is currently done by engineers manually redrawing circuits, iterating slowly because each change has to be checked against physical constraints (power, heat, timing) that are expensive to simulate. A model that can search that design space faster than a human, propose a change, and have it verified against the same physical constraints effectively turns a manual, year-scale process into a machine-assisted, month-scale one. Why this matters beyond the specific percentages: the chips being redesigned are the ones running AI training and inference. If AI-assisted design meaningfully shortens the cycle time for next-generation AI accelerators, the compute-cost curve that underlies every AI business model (including a BBA-relevant angle: the economics behind this week's record-setting AI IPOs) could compress faster than historical hardware cycles suggest. That's a real feedback loop, not marketing language — AI is now a measurable input into the hardware pipeline that produces more AI capability. *(Confidence: Confirmed — real circuit-area and production-pipeline claims, from OpenAI's own published engineering post, corroborated independently by TAAFT. Sources: TLDR AI, TAAFT.)*

## Agents & Automation Watch

Perplexity's Context API is the most directly useful launch today for anyone building scraping or research steps into an automation: instead of writing custom parsing logic per site, an n8n HTTP node can call the API with up to 10 URLs and get back clean Markdown plus metadata (title, author, date, language) in one response, with a freshness parameter so an agent can specify how recent a result needs to be. *(TLDR AI)*

A blog post making the rounds this week measured something concrete about Google's Antigravity coding agent: a 5-minute pause wipes its prompt cache, even a 5-word prompt starts with 13,800-16,800+ tokens of system instructions and MCP schemas before any real work begins, and "refresh the cache before it expires" only buys about 3 extra pings before the cache invalidates anyway. The practical fix the author measured working: disable MCP servers and plugins you aren't actively using in a session, since each one adds to that fixed token floor on every single turn. This generalizes directly to any Claude Code or MCP-heavy n8n setup — idle tool definitions aren't free. *(TLDR AI)*

Prime Intellect's "Model Factory" packages reinforcement learning, fine-tuning, pre-training, and inference into one control plane with automatic node replacement and checkpoint recovery for long-running training jobs — aimed at companies training their own models in-house, not at agent builders working with hosted APIs, but worth knowing as a sign that the "train your own model" tier of the stack is getting productized. *(TLDR AI)*

Nothing new today on agent-harness architecture (memory, durability, observability) specifically — last covered in depth on October 22.

## One Thing to Learn

TLDR AI's deep-dive on "the ski-rental problem" is worth the 20 minutes because it names a decision anyone running agents long enough has already run into without a framework for it. Most model-routing discussion covers the easy half: a classifier scores an incoming request and sends it to a cheap or expensive model. The harder half is a running session — an agent partway through a multi-step coding task — deciding whether to keep paying the cheap model's mistakes or pay once to switch to a better one. That's structurally identical to the "ski rental problem" from classic algorithm theory: you can rent skis every trip for a small fee, or buy them once for a larger upfront cost, and the optimal strategy (rent until your cumulative rental cost would exceed the purchase price, then buy) comes with a provable worst-case guarantee, not just intuition.

The reason this is worth 20 minutes rather than a skim: it gives a concrete decision rule — track the cumulative cost of staying on the current model (wasted steps, retries, wrong turns), and switch once that cumulative cost would have paid for the stronger model's premium from the start — instead of an ad hoc gut call about "is this agent struggling yet." For anyone running multi-step n8n workflows where a model gets stuck in a loop of near-misses, this reframes "should I switch models now" from a vibe into a threshold you can actually compute and log against.

## Rotating: Tools Worth Trying

**Perplexity Context API — Adopt.** This is the one launch today that slots directly into an n8n-based agent stack with no translation needed. The pattern it replaces: a Function node or custom scraper that breaks every time a target site changes its markup. The Context API takes its place as a single HTTP Request node — POST up to 10 URLs, get back clean Markdown, the relevant passages, and metadata (author, publish date, language) in one response, with a freshness flag so a research or monitoring workflow can demand "indexed in the last 24 hours" instead of silently returning stale cached pages. For a workflow that currently pipes raw scraped HTML into an LLM node just to have the model extract the actual content before doing anything useful, this removes an entire unreliable step and replaces it with a vendor that's already solved markup normalization at scale. The adoption cost is low (one API key, one node, pay-per-call) and the failure mode if it goes wrong is graceful (an API error, not a silently malformed scrape) — worth wiring into the next workflow that touches an external webpage.

**Hostinger Connector (for Claude Code/Cursor) — Skip, for now.** This lets a coding agent build a site and push it live from inside a chat session, and its new version has the agent search for the specific action it needs instead of listing every available command — a real usability fix for a chat-driven dev flow. But it's built for a different interaction model than n8n: it assumes a human is in a Claude Code or Cursor session directing the agent turn-by-turn, not a workflow running unattended on a schedule or webhook trigger. There's no indication yet of a programmatic API surface an n8n HTTP node could call directly, which is the bar for "adopt" in an automation stack rather than a coding-assistant workflow. Worth a second look if Hostinger exposes a direct API, but as shipped it's a tool for a person typing into Claude, not a node in a pipeline.

**Notis Hub — Watch, don't adopt yet.** It turns WhatsApp, Telegram, or iMessage into a workspace you design yourself, routing messages to AI processing on subscriptions you already have, so you can hand off tasks by text instead of opening an app. The overlap with an n8n-based stack is real and a little uncomfortable: n8n already has native Telegram and WhatsApp trigger nodes, so for someone who's already built messaging-triggered workflows, Notis Hub is solving a problem that may already be solved. Where it could earn a second look is the opposite direction — as a lightweight way to get *output* from an n8n workflow into a chat interface for a non-technical stakeholder who doesn't want an app, without building that delivery layer from scratch. Not worth migrating existing n8n message-trigger workflows onto it today, but worth a half-hour trial the next time a workflow needs a chat-based front end for someone else.
