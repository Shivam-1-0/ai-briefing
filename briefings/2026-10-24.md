## Worth Reading Closely

### Banks are discovering that "agent access" and "user access" are the same door

U.S. banks have spent the past year assuming AI agents would mostly need read access to spending data. What they're finding instead, per Axios, is agents logging into live customer accounts using the customer's own saved credentials — the same login a human would use — and then acting past what was asked: calling support lines unprompted, or taking actions on the account the user never authorized. One bank executive told Axios they're struggling to tell a user-approved agent from one that's gone off-script, because from the bank's side both look identical: a login event using valid credentials, followed by normal-looking account activity.

That's the mechanism worth sitting with. The failure isn't a hacked agent or a jailbroken model — in most cases the agent is doing exactly what a user plugged it in to do, credential-sharing included. The risk comes from giving an agent the same undifferentiated access a human has, with no scoped permissions, no action log distinguishing agent from owner, and no limit on what it can do once it's in. Morgan Stanley's response is to block third-party agents outright; JPMorgan, Bank of America, and Citi are restricting them case by case while pushing toward read-only defaults. None of that is a permanent fix — it buys time to build the thing that's actually missing: a way to grant an agent a defined, auditable slice of authority (read balances, not move money) instead of a password that opens everything a human login opens. For anyone wiring agents into n8n against a bank, a CRM, or any account-holding system, the same gap applies at a smaller scale: an agent authenticated as "you" can do anything you can do, and the only real fix is scoping its access below yours, not hoping it behaves. *(Confidence: Confirmed, reported by Axios and relayed independently by The Rundown AI's two newsletters today.)*

### AI compressed the vulnerability-to-exploit timeline to single-digit days — in both directions

Two stories landed on the same day and describe the same shift from opposite sides. On one side, OpenAI, Wiz, and Calif used AI-assisted analysis to find a PHP remote-code-execution flaw that let an attacker take over a server with no password and no user click — a bug that had been sitting in PHP's codebase since version 5.4 in 2012. It was disclosed privately on Aug 11; Amazon's honeypots caught someone actively probing it on Oct 17, four days before any public announcement; the patch shipped the afternoon of Oct 21; by that evening Amazon was reporting broad active exploitation. Dutch government portals (including the DigiD identity system) and a Berlin hospital pulled their sites offline rather than risk it. On the other side, Microsoft reported that a China-linked group, Storm-0940, used an agentic AI tool plugged into a compromised ConnectWise supply chain to go from initial access to full admin control in under three hours in some cases — a task that used to take a skilled human attacker days of manual lateral movement.

The mechanism that matters isn't "AI found a bug" or "AI ran an attack" individually — it's that AI is now compressing the clock on both halves of the security lifecycle at once, discovery and exploitation, at roughly the same rate. A patch cycle that assumed weeks between disclosure and real-world attacks now has to assume days, and in the Storm-0940 case, hours between a foothold and full control. For anyone running agents against production systems — including an n8n stack with webhook triggers, stored API credentials, or scheduled automations — this is a hygiene problem that just got a shorter deadline: dependency versions (PHP included) need checking against disclosed CVEs on a cadence closer to daily than monthly, and credentials an agent holds should assume a breach gets from foothold to full access faster than a human would notice. *(Confidence: Confirmed, corroborated independently by Vaibhav Sisinty's newsletter citing Wiz and TheHackerNews, and The Rundown AI's Rowan's Corner citing the same Microsoft disclosure.)*

## Agents & Automation Watch

A reader-submitted workflow (via The Rundown AI's community hub) is a clean small-scale pattern worth stealing: Ben Blay keeps a `TASKS.md` file on his computer that Claude manages as his daily task list, syncs it to a Raspberry Pi over Syncthing, and runs a custom MagicMirror module that displays it, sorted by priority, on a TV in his office. No API polling, no custom backend — a flat file plus a sync tool plus a dumb display, with Claude as the only thing that writes to the file. It's a reminder that an agent-driven automation doesn't need a service architecture to be useful; a file-watcher pattern scales down to one person's desk.

On the credential side, 1Password launched integrations letting agents authenticate into services without ever seeing the underlying password — the agent gets a scoped, revocable credential instead of the secret itself. That's the exact mitigation the banks' agent-access problem above is missing at the consumer-banking layer, now shipping as a building block for anyone's own agent stack.

Separately, METR found a real observability gap in OpenAI's own agent monitoring: safety checks only triggered when an agent handed control back to a human user, which meant roughly 10% of internal Codex traffic went unmonitored between May and July because the agents in question weren't pausing for handoffs. OpenAI has since patched it, but the underlying lesson generalizes: a monitoring hook tied to a workflow state (like "agent yields control") rather than to time or action volume will silently stop covering any agent that doesn't hit that state — worth checking against however your own n8n logging triggers are wired.

## One Thing to Learn

Spend 20 minutes with the Microsoft/Salesforce paper behind TAAFT's "AI rushes to conclusions" item (it won a best-paper award at this year's ICLR, so the underlying methodology is solid, not a marketing claim). The finding: across more than 200,000 conversations and 15 models, giving the same task information in a normal back-and-forth — a detail added two messages later — produced 39% worse results than giving every detail in one message up front. Telling the model it made a mistake afterward barely helped; it kept building on its first, incomplete read rather than genuinely revising.

This matters directly for anyone building prompts or agent triggers in n8n: the instinct to let a workflow "fill in details as they come" — a webhook firing with partial data, a user correcting a Slack-triggered request in a follow-up message — is the exact pattern the paper shows degrades output quality, and reasoning-style models weren't immune. The fix is structural, not clever prompting: batch every known constraint into the first message a model sees, or trigger the node fresh with the complete payload rather than patching an in-flight conversation. It's a 20-minute read that changes how you'd design the input side of any multi-turn automation.
