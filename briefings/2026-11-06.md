## Worth Reading Closely

### Revolut's Claude-to-GLM switch: the 70% gain didn't come from faster coding

Revolut moved roughly 2,000 engineers off Claude Code, which it had been running under strict per-engineer token budgets, and onto GLM 5.3 — an open model from China's Z.ai — self-hosted on 56 Nvidia B200 chips with no per-head limits. The headline numbers: AI spend down to about a tenth of what Claude Code cost, and coding time down 60%. But the number that matters more is lead time — the stretch from picking up a ticket to merging it — which improved 70%, a bigger jump than the coding-speed number alone explains.

The mechanism: under a tight Claude Code budget, engineers saved their tokens for "important" tickets and did everything else — digging through Jira, triaging inboxes, writing status updates — by hand, because nobody wants to burn a scarce token budget on a non-coding task. Once GLM dropped the per-token cost to roughly $0.30 per million tokens with no individual cap, that calculus disappeared. The AI usage didn't just get faster at the core task; it expanded into the surrounding admin work that was previously too "not worth a prompt" to delegate. That's a budgeting effect, not a model-capability effect — and it's the real lesson for anyone running Claude under a metered plan.

Three caveats worth holding onto: Revolut's own AI operations lead called the model's out-of-the-box performance "terrible" before heavy tuning; the model switch and the end of rationing happened simultaneously, so it's not possible to isolate which change did the work; and some developers report GLM struggling in long, complex sessions where Claude still holds up. Revolut itself frames Claude Code as still the "expensive specialist" it reaches for when things get hard — it didn't disappear, it got demoted to harder problems only. *(Confirmed for the headline figures, unaudited — Vaibhav Sisinty / The Register)*

### Two labs just bought the orchestration layer instead of building it

OpenAI acquiring Pierre (Codex's existing code-review tool) and Meta acquiring Conductor (multi-agent task coordination for developers) are separate deals, but they point the same direction: the layer that sits between "a model" and "a working dev workflow" — review, routing, running several agents in parallel — is getting vertically integrated by the big labs rather than left to third-party tooling. For anyone building on n8n with Claude and GitHub as glue, this is the thing to actually watch, not the model benchmarks. The orchestration tools an independent builder relies on today sit in the same category Pierre and Conductor occupied yesterday: useful enough to get bought, which means not guaranteed to stay independent, free, or even available. It's a reasonable argument for keeping your own routing and review logic in workflows you control (n8n, plain scripts) rather than depending entirely on a single vendor's bundled tooling. *(Confirmed — The Rundown)*

## One Thing to Learn

**"Sketch before you build"** — a prompting discipline from The Rundown's Nate Grahek, worth 20 minutes because it maps directly onto the workflow-building you already do in Claude and n8n. The idea: before asking a model to generate the real artifact (a workflow, a deck, a website), explicitly tell it not to build yet — ask it to sketch the plan in a paragraph or two, or as a rough ASCII/bullet outline, and agree on that sketch first. The reasoning is that every session has a finite token budget, and most people "thrash" too late — making expensive, swinging changes to something already fully built, burning credits while still not landing on what they wanted. Sketching costs a fraction of the tokens a full build does, so direction mistakes get caught while they're still cheap to fix. For someone iterating on n8n workflows or Claude-driven automations, this is a direct lever on wasted API spend: make the model commit to a cheap plan, review it, then spend the expensive generation step only once.

## Rotating: Tools Worth Trying

Three tools surfaced in today's newsletters that are relevant to an n8n + Claude + GitHub agent stack. None of them plug into n8n directly — in each case the tool itself targets a different runtime (an IDE, a phone, a Mac menu bar), so the useful export is the pattern it proves out, not the install.

**1. Friday Work** — Open-source failover for coding agents: when Claude hits its usage limit mid-task, it detects the stall and hands the same task to another agent you've already configured, like Codex or Cursor, so the work keeps moving instead of sitting blocked until the limit resets. **Verdict: skip the tool, adopt the pattern.** Friday Work is wired into IDE-based coding agents specifically, which has no surface for n8n's HTTP/webhook-driven workflows to attach to — there's nothing to install here. But the underlying architecture is worth copying directly: an n8n workflow that calls Claude's API can wrap that call in an error-trigger node, catch a rate-limit or quota response specifically (not a generic try/catch), and branch to a second HTTP Request node pointed at a backup provider — GPT, Gemini, or a self-hosted open model — with the same prompt. That turns a single point of failure into a workflow that degrades instead of stopping, which is the exact problem Friday Work solves one layer down, inside a code editor instead of a visual workflow canvas. Worth tacking on, given today's Revolut story: have that fallback branch log which provider actually handled each request, plus its token count, to a Google Sheets or Airtable node. Over a few weeks that log becomes the same kind of cost-per-outcome data Revolut used to justify moving off per-seat Claude budgets — except built from your own workflow instead of someone else's self-reported numbers.

**2. Mika** — A free, open-source agent on GitHub that runs on Android, taps through apps and websites in the background on a user's behalf, and pauses to check in before it spends any money. **Verdict: skip for now, watch the repo.** It's mobile-OS automation — tapping through an actual phone UI — which doesn't map onto a server-side n8n stack at all, so there's no direct adoption path today. What is worth lifting is the specific gate it enforces: spending money is treated as a different risk tier from everything else the agent does, and gets its own confirmation step instead of inheriting whatever approval level the rest of the task had. Translated into n8n, that means any workflow where an agent can trigger a paid API call, place an order, or move money should route through a dedicated "Wait for human approval" node placed immediately before that specific action — not a single blanket approval at the start of the whole workflow, which would let a cheap first step vouch for an expensive last one. A cleaner version still: add an IF node that checks the dollar amount against a threshold you set (say, $5) before the approval step even fires, so small, low-risk actions go through automatically and only the ones actually worth a human's time stop the workflow and wait.

**3. PasteGuard for Mac** — A free menu-bar app that masks emails, card numbers, and API keys the instant they're copied, so sensitive data doesn't land in an AI chat by accident; everything stays on-device, and one keyboard shortcut restores the real values when needed. **Verdict: skip the app, adopt the sanitization step.** It's clipboard-only with no API surface, so it has no way to sit inside an automated pipeline — there's nothing here to wire into n8n directly. But any workflow that feeds scraped web content, inbound emails, or user-submitted form text into a Claude or GPT node is exposed to the exact same leak it's built to prevent, just at pipeline scale instead of clipboard scale. The fix costs one extra node: a Function or Code node running a small set of regex patterns for emails, card numbers, and common API-key formats (`sk-`, `AKIA`, etc.), placed right before the LLM call, that redacts or flags matches before the text ever reaches the model. It's a five-minute addition that closes a gap most n8n agent builders don't think to check until something sensitive actually leaks. Log what gets redacted (not the actual values, just the match type and node) to a separate audit trail, so if an agent ever behaves oddly downstream, there's a record of what it saw stripped out versus what it actually received — useful for debugging and for demonstrating, if this is ever a graded project, that the workflow handles sensitive data deliberately rather than by accident.
